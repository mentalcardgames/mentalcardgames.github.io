# Student Milestones Backlog

This backlog lists the active technical milestones and software engineering packages available for student projects. Each milestone represents a core challenge within our architecture. Rather than being tied to rigid academic ECTS levels, tasks are dynamically scaled and adjusted based on a student's expected workload.

---

## 1. Engine Extraction & Generalization

Our goal is to transition our project from a static Poker game into a general-purpose framework capable of executing any Card Game Description Language (CGDL) description.

### Milestone 1A: Game Engine Crate Extraction
* **Prerequisites:** Familiarity with Rust module systems and `mcg` workspace layout.
* **The Problem:** The current state machine logic for static Poker is tightly coupled with frontend rendering and backend connection supervisors, making it impossible to swap in a CGDL-based game engine.
* **Success Criteria (Deliverables):**
  - [ ] Extract all Poker-specific states, rules, and game FSM code into a dedicated workspace crate (e.g. `crates/poker` or `crates/engine_poker`).
  - [ ] Define a clean, uniform interface/traits that the main application can call to step through states.
  - [ ] Ensure the existing Poker game remains fully playable using the new decoupled boundaries.

## 2. Dynamic UI & Generalized Rendering

The client interface must dynamically adapt to different game states and support alternative user interaction models.

### Milestone 2A: Generalized Game State UI Interface
* **Prerequisites:** Completion of Milestone 1A; familiarity with `egui`.
* **The Problem:** The UI layout is statically hardcoded to Poker table positions. We need a client capable of interpreting and displaying any arbitrary state generated by a CGDL engine.
* **Success Criteria (Deliverables):**
  - [ ] Design a dynamic rendering interface in `egui` that interprets generic zone metadata (e.g. hands, decks, discard piles).
  - [ ] Render action choices dynamically based on the active state machine's available player choices.

### Milestone 2B: Prototypal Game State Frontend Renderer
* **Prerequisites:** Familiarity with `egui` and UI design.
* **The Problem:** Designing a fully generalized renderer is highly complex. A lightweight visual prototype is needed to test FSM-to-UI rendering early.
* **Success Criteria (Deliverables):**
  - [ ] Implement a prototype client that renders a representative subset of dynamic states.
  - [ ] Enable basic interaction loops to prove zone layout and card motion rendering.

### Milestone 2C: Command-Line Interface (CLI) Frontend
* **Prerequisites:** Rust command-line parsing libraries.
* **The Problem:** Testing networking and state transitions inside browser engines is slow and difficult to automate. Developers need a lightweight, headless terminal client.
* **Success Criteria (Deliverables):**
  - [ ] Implement a fully functional text-based game client inside the `mcg-cli` binary.
  - [ ] Format and display the game state clearly using ANSI terminal styling.
  - [ ] Support keyboard input to trigger state actions.

## 3. Tooling & Developer Experience

Providing high-quality tooling encourages developer adoption and makes writing CGDL descriptions much more accessible.

### Milestone 3A: CGDL Language Server Protocol (LSP) & Extension
* **Prerequisites:** Existing Rust CGDL parser crate.
* **The Problem:** Developers writing card game descriptions currently lack syntax highlighting, auto-complete, or active error linting, making writing CGDL highly error-prone.
* **Success Criteria (Deliverables):**
  - [ ] Build a Language Server Protocol (LSP) backend in Rust utilizing the CGDL parser.
  - [ ] Support semantic highlighting, error diagnostics, and basic autocomplete.
  - [ ] Package the language server into a fully functional VS Code extension.

## 4. Cryptography & Zero-Knowledge Proofs (ZKP)

To support true "Mental Poker", we must eliminate the authoritative host model and establish card fairness mathematically.

### Milestone 4A: Cryptographic Protocol & Message Contract Research
* **The Problem:** Running a P2P card game without a server requires cryptographic packets to securely mask cards, shuffle, and prove transitions. We need to define exactly what these packets look like.
* **Success Criteria (Deliverables):**
  - [ ] Research protocols suitable for serverless card validation (e.g. verifiable shuffling, card masking).
  - [ ] Define and implement serializable contract types inside the `shared` crate to support cryptographic exchanges.

### Milestone 4B: Mental Card Game Protocol Design
* **Prerequisites:** Deep understanding of cryptography and math libraries.
* **The Problem:** Current card distribution relies on backend trust. We need to design a cryptographic protocol that mathematically enforces fairness.
* **Success Criteria (Deliverables):**
  - [ ] Design and implement a ZKP library in Rust (potentially using the `arkworks` ecosystem) for shuffling and drawing.
  - [ ] Ensure that proof generation and verification speed are optimized for low-latency gameplay.

### Milestone 4C: Generalized ZKP Engine Integration
* **Prerequisites:** Milestone 4B.
* **The Problem:** Having a standalone crypto library is not enough; the cryptographic validation steps must hook directly into the FSM engine execution loop.
* **Success Criteria (Deliverables):**
  - [ ] Integrate verification checks directly into the CGDL engine's state transitions.
  - [ ] Reject any state transition where the P2P ZKP mathematical validation fails.

## 5. P2P Networking & Trust Architecture

Since each player runs a local node, the network layer must manage peer connection, node discovery, and state synchronization.

### Milestone 5A: P2P Network Consensus & Reliable State Sync
* **Prerequisites:** Basic socket/networking familiarity.
* **The Problem:** In a serverless game, nodes can drop packets or disagree on whose turn it is. We need a reliable messaging layer that guarantees state synchronization across all nodes.
* **Success Criteria (Deliverables):**
  - [ ] Implement robust retry and confirmation pipelines for direct P2P connections.
  - [ ] Implement vector clocks or Lamport timestamps to enforce deterministic ordering of player inputs.

### Milestone 5B: P2P Message Authentication & Connection Verification
* **Prerequisites:** Milestone 5A.
* **The Problem:** Nodes must verify that messages are authentic and protect against Man-in-the-Middle (MITM) attacks during initial handshakes.
* **Success Criteria (Deliverables):**
  - [ ] Implement Ed25519 payload signing for all backend-to-backend P2P packets.
  - [ ] Implement a visual connection verification system (such as an Emoji Hash or Identicon) on the frontend during connection setup.

### Milestone 5C: Decentralized Node Discovery (DHT)
* **Prerequisites:** Milestone 5A.
* **The Problem:** Players must be able to find and connect to each other globally without relying on a static, centralized discovery server.
* **Success Criteria (Deliverables):**
  - [ ] Integrate Iroh's Distributed Hash Table (DHT) for peer-to-peer node discovery.
  - [ ] Handle automatic NAT traversal and hole-punching for global P2P connectivity.

### Milestone 5D: P2P Reliable Broadcast & Consensus Verification
* **The Problem:** Meshed nodes need a reliable way to broadcast state transitions so that all players either collectively accept or collectively veto an action.
* **Success Criteria (Deliverables):**
  - [ ] Research and design reliable broadcast mesh strategies.
  - [ ] Specify and implement consensus state recovery plans for when a node briefly disconnects.

## 6. Messaging Infrastructure & Communication Pipelines

A clean, asynchronous message pipeline is required to handle high-frequency communication between the frontend client, the local backend, and remote nodes.

### Milestone 6A: Centralized Frontend Messaging Interface
* **Prerequisites:** WebSockets and WASM client mechanics.
* **The Problem:** Individual frontend screens manage their own socket logic, leading to connection drops when navigating pages and tight architectural coupling.
* **Success Criteria (Deliverables):**
  - [ ] Establish a single, centralized socket listener thread in the WASM client.
  - [ ] Provide an API allowing individual screens to register callbacks for specific message types.
  - [ ] Decouple screen rendering entirely from connection lifecycle states.

### Milestone 6B: Actor-Inspired Backend Messaging Architecture
* **Prerequisites:** Rust async tasks and channel patterns.
* **The Problem:** The native backend has to manage multiple concurrent socket and P2P connection channels without blocking main thread state calculations.
* **Success Criteria (Deliverables):**
  - [ ] Build a lightweight, actor-inspired messaging architecture utilizing Tokio MPSC channels.
  - [ ] Spawn dedicated lightweight tasks for connection listeners that route messages to a central orchestrator.

## 7. Component Action Interfaces & Protocol Contracts

Clearly defined contract-based APIs ensure robust, testable interfaces between our internal software boundaries.

### Milestone 7A: Comprehensive Component Command & Capability Contracts
* **The Problem:** As the codebase shifts toward decentralized, modular game swapping, the boundary interfaces must be strictly defined so components are easily replaceable.
* **Success Criteria (Deliverables):**
  - [ ] Formulate and implement serializable contract APIs inside the `shared` crate for:
    - *Screens to Frontend Client*
    - *Peer-to-Peer Backend to Backend*
    - *Frontend Client to local Backend (RPC)*
    - *Lobby Control commands*
    - *Game Engine state step inputs*
